# Fairfield Fleet Pipeline

A data pipeline for a made-up company, Fairfield Chemical Transportation, which moves bulk chemicals around South Africa by truck, train and ship.

The ETL is written in C#. SQL Server holds the data in a star schema. Python is only used for two things: making the fake source data, and a small Spark job for the truck GPS pings.

Author: _your name here_

All the data is fake. Customers, assets and orders are generated by `scripts/generate_source_data.py`.

## What it covers

- **Fleet** - 24 road tankers, 6 tank trains, 4 chemical tanker ships. Capacity, home depot, maintenance history.
- **Operations** - every trip: which asset, which order, departure and arrival, tonnes loaded, distance, fuel used, delay reason.
- **Sales** - customer orders: product, tonnes, route, requested delivery date, and what the order is worth.
- **Logistics questions** - was it delivered on time, how full was the asset, what did the fuel cost, which routes make money.
- **Telemetry** - GPS pings from the trucks every 10 minutes (speed and tank temperature).

## How it fits together

```
data/raw/*.xlsx ─────────────► C# (clean + validate) ──► landing tables ──► stored procs ──► core tables ──► reporting views
                                     ▲        │
data/raw/telemetry/*.csv             │        └──► data/rejects (bad rows + reason)
        │                            │
        └──► Spark job ──► data/processed/telemetry_daily.csv
```

| part | tool | why |
|---|---|---|
| cleaning and loading | C# (.NET 8) | the main ETL. `SqlBulkCopy` into SQL Server |
| modelling, revenue, fuel cost | T-SQL | stored procedures and views |
| GPS pings -> daily summary | PySpark | it's the only data with a lot of rows (about 175,000), so a good excuse to use Spark |
| fake data | Python (openpyxl) | quickest way to write a generator |

Honestly 175,000 rows is nothing for Spark and C# could have done it. I wanted to practise it, and telemetry is the kind of data that would get big in real life.

## The source files

In `data/raw`:

| file | what it is |
|---|---|
| `assets.xlsx` | the fleet: trucks, trains, ships |
| `locations.xlsx` | depots, plants and ports |
| `routes.xlsx` | 22 routes, each is road, rail or sea, with the distance |
| `customers.xlsx`, `products.xlsx` | customers and the chemicals carried (with hazard class) |
| `rate_card.xlsx` | price per tonne-km, minimum charge and fuel price for each mode |
| `sales_orders_2025_MM.xlsx` | orders, one file per month |
| `trips_2025_MM.xlsx` | trips, one file per month |
| `maintenance.xlsx` | services, inspections and breakdown repairs |
| `telemetry/truck_pings_2025_MM.csv` | truck GPS pings. These stay as CSV: they come from a tracking system, not from people, and Spark reads CSV directly but can't read Excel files without an add-on |

The business files are Excel workbooks, because that is how this kind of data usually arrives from depots and the sales office. The C# program reads the .xlsx files directly.

The files are messy on purpose: some dates are real Excel dates and some are typed in as text in different formats, values with units in them (`45.5 t`, `570 km`, `R 12,500.00`), duplicates, lower-case ids with spaces, trips for orders that don't exist, a truck recorded on a sea route, loads three times bigger than the tanker, arrival before departure, GPS glitches (speed 999, position 0,0).

## Business rules

**Revenue** (in `core.usp_LoadOrders`):

```
freight = tonnes x route distance x rate per tonne-km for the mode
          (but never less than the minimum charge for the mode)
revenue = freight + hazard surcharge % of the product
```

Cancelled orders have no revenue. Chlorine has a 30% surcharge, glycol has none.

**Trips**: one order can need more than one trip. A 60 tonne road order needs two 30 tonne tankers. Fuel cost is litres x the fuel price for that mode.

**On time**: an order is on time if its last trip arrived on or before the requested delivery date.

**Checks on trips** (in the C# code): the asset must exist, it must be the right type for the route (truck on road, train on rail, ship on sea), and the load can't be more than 5% over its capacity.

## Tables

- `core.DimAsset`, `core.DimLocation`, `core.DimRoute`, `core.DimCustomer`, `core.DimProduct`, `core.DimDate`
- `core.RateCard` - lookup used by the load procs
- `core.FactOrder` - sales, one row per order
- `core.FactTrip` - operations, one row per trip
- `core.FactMaintenance` - one row per maintenance job
- `core.FactTelemetryDaily` - one row per truck per day

Views in `reporting`: order summary, monthly sales, customer sales, asset utilisation, on-time delivery, truck safety.

## Running it

You need:

- .NET 8 SDK
- SQL Server 2016 SP1 or newer, and SSMS
- Python 3.10+ and Java 17 (only if you want to re-run the Spark job or regenerate data)

**1. Database.** Run `sql/01` to `sql/06` in SSMS, in order.

**2. Connection string.**

```
copy appsettings.example.json appsettings.json
```

and change the server name if needed.

**3. Run the pipeline** from the project folder:

```
dotnet run --project src/Fairfield.Etl
```

The first time, this downloads the `Microsoft.Data.SqlClient` package, so it needs internet.

To see only the cleaning step without loading anything:

```
dotnet run --project src/Fairfield.Etl -- --skip-load
```

**4. Check it.** Run `sql/07_data_quality_checks.sql`, then have a look at `sql/08_analysis_queries.sql`.

**Spark (optional).** The output of the Spark job, `data/processed/telemetry_daily.csv`, is already in the repo, so you can skip this. To re-run it:

```
pip install -r requirements.txt
python spark/telemetry_daily.py
```

**Excel.** There is no report export. In Excel use Data > Get Data > From SQL Server and pick one of the `reporting` views, then build a PivotTable on it.

## Known issues

**One data quality check fails, and I left it that way.** "Delivered orders where trips moved less than 95% of the tonnes" finds 55 orders. These are orders marked Delivered where one or more of their trips was rejected in cleaning (duplicate, wrong asset, bad dates), so the trips that are left don't add up to the order. The order is real and so is the revenue, but the fuel cost and delivery date for those orders are incomplete. I don't think silently hiding that is right, but I also haven't decided what the proper fix is. Probably rejected trips should go to someone to correct and reload.

Other things:

- Rates have no dates. If the rate card changes, every old order gets re-priced on the next run.
- No history on any dimension. If a truck's capacity changes, old trips are compared to the new capacity.
- The empty return leg of a trip isn't recorded, so distance and fuel per asset are too low.
- `vw_AssetUtilisation` skips months where an asset did no trips, even if it was in maintenance.
- Maintenance records are insert-only. A corrected cost in the file is not picked up.
- The Excel reader (`XlsxFile.cs`) is hand-written. It only reads the first sheet, expects the header in row 1, and would be better replaced with a library like ClosedXML.
- In the reject files, a date that was a real Excel date shows as a serial number (45666.915 instead of 2025-01-09 21:58), which makes the rejects harder to read.
- The CSV reader is hand-written too and can't handle a line break inside a quoted value.
- The landing load isn't in a transaction. If it fails half way, some landing tables are new and some are old. (The core load is in a transaction.)
- No unit tests for the C# code.
- Logging is just `Console.WriteLine`.
- Landing tables are fully reloaded on every run, all 12 months.
- Telemetry is trucks only. Trains and ships would have position data too.
- The speed limit (80 km/h) and temperature alert (45 C) are hard-coded in the Spark job. Temperature limits should be per product.
- The Spark job collects the result to pandas to write one CSV. Fine for 3,774 rows, wrong for real volumes (should write Parquet).
- Telemetry isn't linked to trips, only to the truck and the day.
